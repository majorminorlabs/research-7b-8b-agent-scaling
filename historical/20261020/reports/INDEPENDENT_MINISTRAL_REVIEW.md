# Independent review: Ministral 3B versus 8B

19 September 2026. This review used preserved requests, responses, simulator events, resource samples, the frozen scorer and fixtures, historical 3B records, model manifests, and server metadata. It did not run either model or replay a benchmark task. The earlier forensic classification was treated as a hypothesis.

## Decision

**B — VALID WITH LIMITATIONS** for the recorded 8B observation. The 8B server loaded the identified GGUF and returned HTTP 200 for all 68 chat requests across Q01–Q07. The controller marked every task `complete`; the frozen scorer independently gives **17/80** from the preserved simulator events. No response has `finish_reason=length` (67 `tool_calls`, one `stop`; largest single completion 202 tokens against the 768-token limit). The server log records `truncated = 0` and no load, allocation, or transport failure. These facts rule against **C, invalid execution** on the available evidence. The behavioral trace and score are sufficiently determinate to rule against **D** for the *observed run*. The protocol deviations and incomplete metadata rule out **A**.

## The resource rule and possible causal mechanism

The original `protocol/protocol.json`, `runner/RESOURCE_RECORD.md`, scientific freeze, README, and final report define a local-fit rule: at least 5.0 GiB **available system RAM** throughout, no candidate-attributable swap, and no memory instability. It exists to distinguish whether an evaluated model fits the specified ThinkPad budget from what it scores on the seven tasks. The original publication retained Qwen3's 17/80 despite a 4.95 GiB finalist-set minimum and Nemotron's scored but resource-ineligible result. A resource FAIL therefore was **not intended to erase or invalidate capability points**. It does invalidate a claim that the candidate qualified for that local resource budget.

The 8B minimum available RAM was 4.589 GiB. Q01–Q04 remained above the floor (5.647, 5.496, 5.279, 5.081 GiB); Q05–Q07 crossed it (4.861, 4.698, 4.589 GiB). Sampled swap used remained zero. The lower free-memory margin can increase paging or contention and thus latency. It could affect output if memory pressure caused failed allocations, context loss/truncation, a runtime change of device or numerical path, or a request timeout. The preserved log and responses show none of those events. The run completed the 12-turn limit in Q05 and Q07 rather than a wall-time timeout, and there is no generation or context truncation. Available RAM below an administrative threshold is not itself a mechanism that changes the loaded weights or greedy token choice. GPU memory, page faults, and exact tensor placement were not logged, so a subtler effect cannot be excluded. The record does **not** establish a memory-caused capability loss. The Q01 and Q03 deficits occurred before the RAM floor was crossed, while Q05 improved below it; Q07's failure coincides with low RAM but has no demonstrated memory failure.

## Model and request comparability

The historical manifest pins `mistralai/Ministral-3-3B-Instruct-2512` to a Bartowski GGUF, SHA-256 `fec9d28c7f8dab7c6857d54b56c8264cce57d6f6d9003bd4110f6457f071c65a`, explicitly described as a llama.cpp **imatrix** Q4_K_M quantization of a BF16 source. The 8B file is the official Mistral Instruct 2512 GGUF Q4_K_M, SHA-256 `33e7a72cf5e6e2cfc2f2847075acc013d68bba023e35310cef86b5cf8fdca761`, pinned in `manifests/availability_check.json`; the recorded server path and `models/8b-gguf/model-sha256.txt` agree. These are sibling *Instruct* models, but `Q4_K_M` names a storage format, not an identical quantization error profile. Calibration data, source checkpoint precision, converter version, and quantization choices can alter weights and greedy token ranking; one altered call can change all later simulator state. The 8B artifact's exact quantizer recipe is not documented in the preserved record. This difference materially weakens a **parameter-size-only** inference, although it does not make either artifact's recorded behavior invalid. Mistral's [8B GGUF card](https://huggingface.co/mistralai/Ministral-3-8B-Instruct-2512-GGUF) confirms the official Instruct Q4_K_M offering; it does not establish quantizer equivalence to Bartowski's 3B file.

The first system and user messages and the tool definitions match exactly between paired raw records; temperature 0, seed 0, max 768 tokens, the 16,384 context, frozen llama.cpp build (`b11028-972d2313b`), and Vulkan/RADV also match where recorded. The historical first-request JSON in each task contains later assistant/tool messages, so its logged message count is not a faithful first-turn snapshot; the two initial messages and tools remain comparable. Prompt-token *counts* are recorded, but the exact rendered prompt strings and token sequences are unavailable. The historical 3B `/props` dump records its native GGUF template and `supports_reasoning_effort:false`; no corresponding 8B `/props` or rendered-template dump was preserved. Native templates may therefore differ in more than the model-name text. Exact launch options, tensor offload, KV settings, and GPU memory are likewise not reconstructable for both sides.

Unlike the historical request JSON, every 8B request includes `reasoning_effort:"none"` and `reasoning_format:"none"`. At the **frozen llama.cpp commit**, [server documentation](https://github.com/ggml-org/llama.cpp/blob/972d2313bc0bf0a45f634f77d95c9fb03aeab12/tools/server/README.md) says `reasoning_effort:none` disables reasoning/thinking and `reasoning_format:none` leaves reasoning text unparsed in content. Thus they must not be dismissed as necessarily inert. The separate [Mistral model card](https://huggingface.co/mistralai/Ministral-3-8B-Instruct-2512) identifies Instruct and Reasoning as distinct variants; the observed model is Instruct. The 3B props indicate no reasoning-effort support, and the 8B responses show normally parsed tool calls, without visible thinking text. These facts make a large effect **unproven**, but without 8B template capabilities or an omitted-fields control, an 8B-specific prompt or parser effect remains plausible. `reasoning_format` is mainly a response-parsing setting; `reasoning_effort` could alter template behavior if the embedded 8B template recognizes it.

## Direct trace and scoring audit

The frozen scorer and fixtures are byte-for-byte identical to the historical files (SHA-256 `92e0dc15a3b8ca8836108c4ad30725af56f497c3f897a00c0f39ee1be4d7cb2d` and `4de90399bb610afea4d04a18a12a56dc313939000d630f23b232807564f3d50b`, respectively). Reapplying `score_run` to the preserved event streams gives both totals above. The key scientific limitation is **construct validity**, not a disagreement in arithmetic: several scoring atoms are awarded by tool-name or read-count proxies even when the model did not establish the named fact or achieve the objective.

## What may be reported, and what cannot be inferred

**Report the observed benchmark result:** historical 3B 25/80 in each of three observations versus 8B 17/80 in one observation, with 8B resource eligibility **FAIL** (4.589 GiB minimum versus 5.0 GiB required). Label these as frozen-scorer points and identify the severe Q07 dependence. Do not call the two 8B scorer completion atoms two verified task completions; the raw Q02 and Q05 final states do not support that interpretation.

**Do not claim that 3B is the more capable model.** The result is one limited paired comparison of two distinct quantized artifacts. The 8B request fields and unknown embedded template differ; the 8B fails the local resource rule; it has only one seven-task observation; and the dominant 3B Q07 advantage includes points whose atom names are contradicted by the 3B's final plan. The traces show genuine behavioral differences in this setup, but the record cannot separate model scale from quantization/template/request effects or convert partial proxy points into a general capability ranking. In that *causal scaling* sense the answer remains indeterminate, while the observed run itself is **B**.

## Controlled replication, kept separate

A controlled replication is scientifically useful and does **not** invalidate this observation. The minimum first experiment to test the resource hypothesis is a **new, preregistered 8B observation** with the same pinned GGUF, frozen llama.cpp build, backend, requests (including both reasoning fields), fixtures, scorer, and limits, but with at least 5 GiB available RAM at all samples and zero inference swap. Save it under a new run ID and preserve the exact launch command, model hash, `/props`/GGUF template metadata, rendered prompt or `/apply-template` result, effective device/tensor placement, VRAM and page-fault telemetry, raw requests/responses, server log, and simulator events. Compare it to the original as a resource contrast, never as a replacement.

To test the **scaling** claim, additionally preregister a distinct paired study of 3B and 8B under the same compliant host/runtime and request-field policy, with GGUFs prepared through the same documented quantizer procedure and calibration policy from pinned source checkpoints. Use the same Q01–Q07 tasks, fixed scorer, and repeated full sets; record native template renderings and any unavoidable model-specific template difference. A separate 8B omitted-fields condition isolates the reasoning-field change before treating it as harmless. Put all new data under a new protocol version and paths; leave the frozen v1 study and this first 8B observation untouched. These are recommendations only; no run is authorized or performed by this review.
